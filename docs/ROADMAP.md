# מפת הפיתוח של הבית המסודר

המטרה היא להתקדם במנות קטנות, כאשר בסוף כל שלב האפליקציה נשארת עובדת ומכוסה בבדיקות.

## הנחת המוצר הנוכחית

בגרסה הנוכחית קיים מרחב עבודה משותף אחד:

- משתמשים יכולים להירשם ולהתחבר.
- כל משתמש מחובר יכול לראות ולנהל את רשימת המשימות המשותפת.
- משימה יכולה להיות משויכת למשתמש רשום אחד או להישאר ללא אחראי.
- השיוך מציין מי אחראי לביצוע; הוא אינו מגביל צפייה או עריכה.
- אין כרגע `households`, `memberships`, תפקידים או מעבר בין מרחבי עבודה.

ריבוי בתים והרשאות לפי בית נשארים אפשרות עתידית בלבד, ולא יכתיבו את הסכמה או ה־API כעת.

## שלב 1 — בסיס מקומי עובד ✅

- FastAPI, SQLite וממשק עברי.
- יצירה, הצגה, השלמה ומחיקה של משימות.
- תיעוד API ובדיקות בסיסיות.

## שלב 2 — סדר וארכיטקטורה ✅

- `api/` מטפל ב־HTTP.
- `services/` מכיל כללים עסקיים.
- `repositories/` הוא המקום היחיד שמדבר SQL.
- `schemas.py` מגדיר ומאמת מבני נתונים.
- `main.py` מרכיב את האפליקציה.
- עריכת משימה קיימת זמינה דרך ה־API והממשק.

## שלב 3 — משתמשים, הרשמה והתחברות

סדר המימוש:

1. טבלת `users` עם שם, דוא״ל ייחודי, hash סיסמה וזמני יצירה.
2. פונקציות גיבוב ואימות סיסמה עם בדיקות יחידה.
3. הרשמה, התחברות, התנתקות ו־`GET /api/auth/me`.
4. Session אקראי בעוגיית `HttpOnly`; אין JWT בשלב הזה.
5. הגנה על פעולות המשימות כך שרק משתמש מחובר יוכל להשתמש בהן.
6. מסכי הרשמה והתחברות ומצב משתמש מחובר בממשק.

## שלב 4 — שיוך משימות למשתמשים

1. הוספת `assignee_id` אופציונלי ל־`tasks` כ־FK אל `users`.
2. מעבר מבוקר מהשדה הטקסטואלי `assignee` אל הקשר החדש.
3. החזרת פרטי אחראי נוחים להצגה בתשובות ה־API.
4. בחירת אחראי מתוך משתמשים רשומים בטופס יצירה ועריכה.
5. אפשרות מפורשת להשאיר משימה ללא אחראי.
6. בדיקות למשתמש קיים, מזהה לא קיים, ביטול שיוך ורגרסיה של נתונים קיימים.

## שלב 5 — הקשחת הזרימה המשותפת

1. מדיניות ברורה למשתמש מושבת או מחוק שמשויכות אליו משימות.
2. הגבלת קצב לכניסה ולהרשמה.
3. הגנת CSRF לפעולות משנות מצב כאשר האפליקציה נפרסת מחוץ ל־localhost.
4. בדיקות אינטגרציה של הרשמה → התחברות → יצירה → שיוך → עריכה → התנתקות.
5. תיעוד פרטיות: כל משתמש רשום רואה את המידע המשותף.

## שלב 6 — משימות חוזרות אמיתיות

1. הפרדת תבנית החזרה מהביצוע היומי.
2. שדות תדירות, יום בשבוע ותאריך ביצוע הבא.
3. יצירת מופע חדש למשימה יומית או שבועית.
4. מניעת יצירה כפולה.
5. בדיקות זמן, אזור זמן ושעון קיץ.

## שלב 7 — יכולות מוצר נוספות

המשך הפיתוח ייקבע לפי ערך למשתמש: רשימות קניות, אזורים בבית, תזכורות, קבצים, תמונות ודשבורד שבועי.

## שלב 8 — תשתית בדיקות אוטומטיות

1. חלוקת Pytest ל־unit, ‏API integration ו־end-to-end.
2. fixtures משותפים למסד זמני, משתמשים, Sessions ומשימות.
3. בדיקות API ישירות ומהירות באמצעות `TestClient`/`httpx`.
4. Playwright עם Pytest לתרחישי UI קריטיים בדפדפן אמיתי.
5. traces, צילומי מסך ווידאו בכשל בלבד.
6. בדיקות smoke נגד image ארוזה ונגד סביבת staging.

## שלב 9 — CI ו־Docker

1. CI על כל Pull Request: unit, API, lint ובדיקות UI קריטיות.
2. `Dockerfile` רב־שלבי, `.dockerignore` ומשתמש runtime שאינו root.
3. `compose.yaml` לפיתוח, בדיקות והרצה מקומית עקבית.
4. image יחידה וזהה שעוברת בדיקות ונפרסת בהמשך ל־staging/production.
5. סריקת image ותלויות ותיעוד גרסאות.

## שלב 10 — PostgreSQL ומיגרציות

1. הפרדת תצורת DB באמצעות `DATABASE_URL`.
2. Alembic ומיגרציות קדימה/אחורה, כולל מעבר מ־SQLite.
3. PostgreSQL ב־Compose וב־CI.
4. connection pooling, timeouts וטרנזקציות ברורות.
5. בדיקות migration, גיבוי ושחזור.
6. Sessions ונתוני האפליקציה נשמרים במסד משותף, לא בזיכרון process.

## שלב 11 — staging ותצפיתיות

1. סביבת staging עם HTTPS ותצורה נפרדת.
2. לוגים מובנים ללא סודות, סיסמאות, hashes או tokens.
3. endpoints נפרדים ל־liveness ול־readiness.
4. מדדי בסיס, ניטור שגיאות והתראות.
5. הרצת smoke ו־Playwright נגד staging לאחר פריסה.

## שלב 12 — Kubernetes

1. Deployment ו־Service לאפליקציה ה־stateless.
2. ConfigMap לתצורה ו־Secret לסודות; סודות אינם נשמרים ב־Git.
3. readiness/liveness/startup probes, resource requests/limits ו־graceful shutdown.
4. migrations כ־Job יחיד לפני rollout, ולא בעת startup של כל replica.
5. Ingress/Gateway עם TLS ו־PostgreSQL מנוהל או מחוץ ל־Pods של האפליקציה.
6. rollout/rollback מתועדים, PodDisruptionBudget ו־autoscaling רק לאחר מדידה.

## כללי אי־חסימה כבר מהיום

- כל תצורה סביבתית מתקבלת ממשתני סביבה או שכבת settings, לא מערכים קשיחים בקוד.
- קוד עסקי אינו תלוי ב־SQLite; פרטי SQL וסוג החיבור נשארים בשכבת הנתונים.
- אין לשמור Session או מצב אפליקטיבי חשוב בזיכרון process.
- קבצים מקומיים אינם מקור אמת עתידי; אחסון מתמשך מקבל abstraction מפורש.
- `/health/live` בודק שה־process חי; `/health/ready` בודק שהאפליקציה מוכנה לקבל תעבורה.
- migrations אינן רצות אוטומטית בכל process או replica.
- כל image ניתנת להגדרה חיצונית, רצה כמשתמש שאינו root ונסגרת באופן graceful.
- בדיקות אינן תלויות ב־localhost קשיח; כתובת הבסיס ניתנת להגדרה.
- אותו artifact שנבדק ב־CI הוא זה שנפרס, ללא build חדש לכל סביבה.

## כלל סיום לכל שלב

שלב נחשב גמור רק כאשר:

- היכולת עובדת בממשק ולא רק דרך `/docs`.
- יש בדיקות לדרך התקינה ולשגיאות המרכזיות.
- הבדיקות משתמשות במסד זמני ואינן משנות את מסד הפיתוח.
- אין שגיאות בקונסול או בשרת.
- ה־README וה־Roadmap מעודכנים.
- השינוי נשמר ב־commit קטן וברור.
